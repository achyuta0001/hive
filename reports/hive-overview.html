Internal Project Overview

Hive — a Knowledge Compiler

Turns scattered, overlapping, and contradicting documentation into a single trustworthy source of truth — built to feed AI coding agents without burning tokens on repeated search.

Stage: MVP, core loop validated 2 of 3 connectors built Synthesis quality validated on real content
The Problem

Documentation sprawl costs tokens, time, and trust

Teams keep knowledge in Notion, Confluence, and markdown wikis that drift out of sync with each other. When an AI coding agent (or a new engineer) needs an answer, it has to re-search the same scattered, overlapping sources every time — expensive in tokens, slow, and it can silently surface outdated or contradictory guidance with no warning.

Repeated, expensive search

Every agent session re-discovers the same knowledge from scratch via RAG search over raw documents, instead of reading one compiled answer.

Silent contradictions

Two documents disagree — e.g. "run migrations before deploy" vs "after" — and whichever one gets retrieved first wins, with no flag that a conflict exists.

The Solution

One compiled, conflict-aware source of truth

Hive ingests documents from any source, normalizes them into one canonical schema, and uses an LLM to merge overlapping content into a single clean page — explicitly flagging any contradiction instead of silently picking a side.

Cost discipline is built into the architecture

An LLM is only ever called on content that changed since the last sync. Everything else is skipped automatically — the pipeline's biggest lever for keeping this affordable at scale.

Never guess on a contradiction

If two sources disagree, the compiler is required to flag it rather than pick one — treating a conflict as something a human should resolve, not something an LLM should paper over.

Sources are swappable, the core isn't

Adding a new source (Notion, Confluence) only ever touches the connector layer. Everything downstream — the schema, the diffing, the compiling — stays untouched and source-agnostic.

Where It Stands Today

Core loop validated on real content, from two sources

The full pipeline now runs end to end against both markdown files and a live Notion workspace: ingest, deduplicate against prior runs, and compile into a merged wiki page. Synthesis quality was the open question after the first round of testing — it's now resolved with a capable model, verified both on deliberately-contradicting test fixtures and on unrelated real content pulled live from Notion.

The earlier finding — a small free local model tended to concatenate documents rather than synthesize them, and could silently drop a source — is resolved for the compiler's default configuration. A stronger model now reliably merges content, correctly identifies real contradictions, and correctly reports "no conflicts" when none exist rather than inventing one. A code-level check now also verifies every compile before it's saved, so a quality regression would be caught immediately rather than silently shipped.

What's Next

Roadmap

  1. Automatic topic clustering — group related documents by similarity instead of batching everything together, using lightweight local embeddings.
  2. Rule-based conflict pre-checks — catch obvious contradictions (dates, numbers, mismatched metadata) without spending an LLM call, reserving the model for genuinely ambiguous cases.
  3. Confluence connector — the remaining planned source, saved for last due to a more complex API surface (v1/v2 split, XML storage format).
  4. A serving layer — once there's a compiled wiki worth querying, add simple search so agents and engineers can retrieve answers directly.
  5. OAuth for connectors — deferred deliberately; today's connectors use manually-created integration tokens, which is the right amount of complexity for a single-user setup. Revisit if Hive ever needs to support multiple users or workspaces.
